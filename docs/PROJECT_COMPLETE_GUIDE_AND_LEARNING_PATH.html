1. Executive Summary & Problem Formulation

In Indian digital communication (WhatsApp, Instagram, X/Twitter, YouTube), Telugu speakers predominantly communicate in Tanglish—colloquial Telugu written in the Latin alphabet intermingled with English loanwords, technical terminology, abbreviations, and informal chat syntax.

The Core Challenge: Standard Machine Translation systems (Google Translate, Bing) fail catastrophically on code-mixed text because they attempt to phonetically transliterate English loanwords into Telugu script (e.g., college → కోల్లెగె, interview → ఇంతేర్విఎవ్). This degrades readability and downstream comprehension.

System Objective: Given an input sequence $X = (x_1, \dots, x_{T_x})$, the model must:

  1. Accurately transliterate colloquial Romanized Telugu morphemes to pristine Telugu Unicode script (e.g., naku ivala → నాకు ఇవాళ).
  2. Dynamically recognize embedded English loanwords and route them through a Pointer-Generator Copy Gate, retaining Latin characters with 100% fidelity.
  3. Provide multi-modal generation: Standard Normalized, All Telugu Script, All Romanized Tanglish, and Pure English Semantic Translation.

Level 1: Linguistic Foundations of Tanglish

Telugu is an abugida script with 56 primary characters. Tanglish uses the 26-letter Latin alphabet to represent these sounds phonetically. Because there is no official standardized spelling, users write with huge variations:

  • Vowel elongation: chala → chaala, chaalaa ("very").
  • Aspiration omission: dhanyavadalu → danyavadalu ("thanks").
  • Intra-sentential loanwords: English nouns/verbs are embedded directly into Telugu grammar (e.g., college lo, interview undi).

Level 2: Data Engineering & Zero-Leakage Hashing

Standard random splits leak identical sentences across train and test, producing artificially inflated metrics. We implemented deterministic SHA-1 bucket hashing on target sentence groups: 

def bucket(group: str, salt: str = "tecm-v1") -> int:
    return int(hashlib.sha1(f"{salt}:{group}".encode()).hexdigest()[:8], 16) % 10000

def assign_split(group: str, valid_frac: float = 0.1, test_frac: float = 0.1) -> str:
    b = bucket(group) / 10000
    if b < test_frac: return "test"
    if b < test_frac + valid_frac: return "valid"
    return "train"

Held-out vocabulary words (e.g., interview, charger, canteen) are quarantined strictly into test_unseen_words.jsonl to test true out-of-domain generalization.

Level 3: Character-Level Tokenization

Subword tokenizers (BPE) break under informal character elongation, splitting unseen variants into rare subwords or <unk>. A character tokenizer maps ~180 characters (Latin, Telugu Unicode 0x0C00–0x0C7F, digits, punctuation), reducing the out-of-vocabulary rate to 0.0%.

Level 4: Neural Architecture: BiGRU + Pointer-Generator Gate

The encoder is a 2-layer Bidirectional GRU yielding concatenated states $h_i = [\vec{h}_i; \overleftarrow{h}_i] \in \mathbb{R}^{2 d_h}$. At each decoder step, the Pointer-Generator Copy Gate calculates: 

p_gen = torch.sigmoid(self.p_gen_layer(torch.cat([feat, e], -1)))
vocab_probs = F.softmax(logits, dim=-1)
p_final = p_gen * vocab_probs
p_final.scatter_add_(1, src_mapped, (1.0 - p_gen) * w)
logits = torch.log(p_final.clamp(min=1e-12))

When encountering an English loanword, $p_{\text{gen}} \rightarrow 0$, copying the Latin character directly from the input sequence!

Level 5: Attention Mechanisms Compared

We evaluated three distinct attention architectures in src/attention/attention.py:

  • Bahdanau (Additive): $e_{t, i} = v^T \tanh(W_q s_{t-1} + W_k h_i)$. Evaluated before RNN step.
  • Luong (General): $e_{t, i} = s_t^T W_a h_i$. Evaluated after RNN step with input feeding.
  • Scaled Dot-Product (Winner): $e_{t, i} = \frac{(W_q s_t)^T (W_k h_i)}{\sqrt{d}}$. Scaling prevents gradient vanishing in softmax.

Level 6: Loss Functions & CUDA FP16 Training Dynamics

Trained using Cross-Entropy with Label Smoothing ($\epsilon = 0.05$) to prevent over-confidence. Mixed-precision FP16 via torch.cuda.amp.autocast() cut memory in half and doubled speed on the NVIDIA RTX 4060 GPU.

5. End-to-End System Execution Flow: Step-by-Step Lifecycle

Here is what happens when a user types: naku ivala college lo important interview undi:

  1. Input Ingestion: The Web Studio (or Chrome Extension) sends an HTTP POST request to /omni/process with payload {"text": "naku ivala college lo important interview undi"}.
  2. Modality Detection: detect_modality() in src/pipeline/omni_processor.py scans characters. It detects Romanized characters mixed with English lexicon tokens (college, interview) and classifies it as code_mixed.
  3. Model Registry Lookup: ModelRegistry retrieves the active production_sota checkpoint cached in GPU VRAM (NVIDIA RTX 4060).
  4. Character Tokenization: CharTokenizer converts input characters into a 1D integer tensor $[1, 48, 12, 55, \dots]$.
  5. BiGRU Encoding: The 2-Layer BiGRU encoder processes the sequence forward and backward, producing hidden state tensor $H \in \mathbb{R}^{B \times T_x \times 384}$.
  6. Attention & Pointer-Generator Decoding:
    • For Telugu tokens (naku → నాకు, ivala → ఇవాళ): Scaled Dot-Product Attention focuses on phonetic source characters, $p_{\text{gen}} \approx 0.95$, and the model samples from Telugu Unicode vocabulary.
    • For English loanwords (college, interview): The model detects Latin character sequences, $p_{\text{gen}} \approx 0.02$, and the gate copies Latin characters directly from the source sequence!
  7. Beam Search Decoding: Vectorized beam search ($K=4$) ranks hypotheses with length penalty $\alpha=1.0$, producing the best sequence: నాకు ఇవాళ college లో important interview ఉంది.
  8. Multi-Modal Generation: The OmniProcessor synthesizes 4 options:
    1. Standard Normalized: నాకు ఇవాళ college లో important interview ఉంది
    2. All Telugu Script: నాకు ఇవాళ కాలేజ్ లో ఇంపార్టెంట్ ఇంటర్వ్యూ ఉంది
    3. All Tanglish: naaku ivaala college lo important interview undi
    4. Pure English Translation: "I have an important interview at college today"
  9. Response & Audio TTS: The response is returned in ~8.2 ms. The Web Studio renders cards, triggers Web Speech TTS audio, and displays real-time suggestions.
  10. Active Learning Feedback: User rating (👍/👎) is saved to data/feedback.jsonl.

6.3 Anticipated Technical Viva Questions & Bulletproof Answers

Q1: Why did you choose a 2-Layer BiGRU instead of a Transformer or Large Language Model (LLM)?
Answer: Large Language Models (like LLaMA or GPT-4) contain billions of parameters and take 300ms to 2 seconds per inference, requiring cloud clusters. For real-time keyboard typing and browser extensions, latency must be under 10ms. Furthermore, Transformers lack recurrent inductive biases and require hundreds of thousands of sequences to learn character-level alignments effectively. Our 2-Layer BiGRU has 3.05M parameters, runs in ~8.2 ms on our RTX 4060 GPU, and achieves superior character alignment on medium-sized corpora.
Q2: How exactly does the Pointer-Generator Copy Mechanism work?
Answer: The Pointer-Generator network computes a scalar generation probability $p_{\text{gen}} = \sigma(W_{\text{ptr}} [s_t; c_t; e(y_{t-1})] + b_{\text{ptr}})$. The final probability distribution is: $$P(w) = p_{\text{gen}} P_{\text{vocab}}(w) + (1 - p_{\text{gen}}) \sum_{i: x_i = w} \alpha_{t, i}$$ When encountering English loanwords, the network drives $p_{\text{gen}} \rightarrow 0$ and uses the attention weights $\alpha_{t, i}$ as a pointer to copy Latin characters directly from the source sequence into the output.
Q3: What is "Zero-Leakage Splitting" and why is a random train/test split invalid here?
Answer: In code-mixed transliteration, one clean Telugu target sentence often has multiple noisy Romanized variants (e.g., chala, chaala, chaalaa). If you perform a naive random split, variant A lands in train and variant B in test. The model simply memorizes the target, producing artificially high BLEU scores. Our zero-leakage hash splitting groups all variants by target lemma and hashes them using SHA-1. All variations of a sentence or vocabulary root are guaranteed to remain strictly in train or strictly in test, never both.
Q4: Why Character-Level Tokenization over Byte-Pair Encoding (BPE)?
Answer: In informal social media Tanglish, users elongate characters for emotional emphasis (e.g., chaaaaala, plzzzzz). Subword tokenizers (like BPE) fragment these unseen patterns into rare subwords or <unk>, destroying the word. A character tokenizer handles arbitrary character elongation with a compact vocabulary of ~180 tokens and achieves a 0.0% Out-of-Vocabulary rate.
Q5: How do you measure the performance of your system?
Answer: We evaluate across four complementary metrics: 1. Character Error Rate (CER): Levenshtein distance at character level (achieved 5.37%). 2. chrF: Character n-gram F-score capturing morphological correctness (achieved 91.29). 3. BLEU: Modified n-gram precision with brevity penalty (achieved 79.84). 4. English Loanword Accuracy: Verifies that English words are preserved with 100% fidelity without phonetic corruption.
Q6: How is the sub-10ms inference latency achieved in production?
Answer: Three optimizations: 1. PyTorch CUDA FP16: Automatic mixed precision running on NVIDIA RTX 4060 Tensor Cores. 2. Vectorized Beam Search: Batch decoding executed as tensor matrix operations rather than slow Python loops. 3. VRAM Model Caching: Pre-warmed model weights held in GPU memory via the singleton ModelRegistry, eliminating disk I/O during API calls.
